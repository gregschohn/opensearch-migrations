## 2. Rust foundation — PROVED

### 2.1 Protobuf generation from the unchanged shared schema

`capture-wire/build.rs` generates from
`TrafficCapture/captureProtobufs/src/main/proto/TrafficCaptureStream.proto` in place. It asserts the
path resolves rather than vendoring a copy, so the Rust proxy and the Java replayer cannot drift
onto different schemas.

Verified in the generated output: every field number and oneof tag is preserved —
`TrafficObservation.Capture` tags `2,3,4,5,6,8,9,10,11,12,14,15,16,17,19`;
`CaptureRecord.Payload` tags `1,2,3`; `TrafficStream.Index` tags `3,4`;
`TrafficStream` `connectionId=1, subStream=2, nodeId=5, priorRequestsReceived=6,
lastObservationWasUnterminatedRead=7` with `8` reserved;
`TrafficObservation.ts=1, connectionObservationSequence=18`.

`bytes` fields are mapped to `bytes::Bytes` so captured payloads can be sliced from the connection
read buffer without copying.

### 2.2 librdkafka native linking — PROVED on the development host

`rdkafka 0.39` with features `cmake-build, ssl, sasl, zstd, libz` compiles and links. The vendored
CMake cache confirms the features the capture protocol and supported Kafka properties require:

```text
WITH_SSL:BOOL=1
WITH_SASL:BOOL=1
WITH_SASL_OAUTHBEARER:UNINITIALIZED=1
WITH_SASL_SCRAM:UNINITIALIZED=1
WITH_ZLIB:BOOL=1
WITH_ZSTD:BOOL=1
WITH_CURL:BOOL=0
```

`WITH_SASL_OAUTHBEARER=1` is the prerequisite for the MSK IAM path. `WITH_CURL=0` means
librdkafka's OIDC token-retrieval method (`sasl.oauthbearer.method=oidc`) is unavailable; the MSK
IAM design does not need it, because the proxy generates the SigV4 token itself and installs it
through the OAUTHBEARER token-refresh callback. This must be re-proved on the AL2023 release image,
not just here — a prior attempt at this rewrite failed at runtime on a `libsasl2.so.2` SONAME
mismatch between a Debian builder and an AL2023 runtime.

### 2.3 Java-compatible partition routing — PROVED (cross-language)

Java (`CaptureRoutingState.java:364-366, 659-668, 690-692`):

```text
partition = sortedAscendingUnique(assignedPartitions)[
    Utils.toPositive(Utils.murmur2(connectionId.getBytes(UTF_8))) % size ]
```

`validateRoutingPartitions` builds the list from a `TreeSet<Integer>` (unique, ascending) and
rejects any partition outside `[0, topicPartitionCount)`.

Golden vectors were generated by running the real `org.apache.kafka.common.utils.Utils` from
kafka-clients 4.2.0 — the exact client the Java proxy uses — over 68 connection ids: Netty-style
long-form ids, the empty string, lengths 1-8 spanning Murmur2's 4-byte block boundary, multibyte
UTF-8 (`ÿ`, `éè`, `中文`, `😀`, `café`), and 48 seeded pseudo-random ids; each crossed with 8
assigned-partition sets.

`capture-kafka::routing_hash` reproduces **all 68 hashes and all 544 routing decisions with zero
mismatches**. Generator preserved at `qualification/java-fixtures/GenVectors.java`; fixture at
`crates/capture-test-support/fixtures/murmur2-golden.json`; test at
`crates/capture-kafka/tests/routing_hash_golden.rs`.

Note that `Utils.toPositive` masks the sign bit rather than taking an absolute value, so `i32::MIN`
maps to `0`. An `abs()`-based port would panic or overflow instead.

## 3. Discrepancy register

Each row cites both sides. "Resolution" is what the Rust implementation does. Rows marked
**OWNER** change externally visible behavior and are not implemented until the owner rules.

### 3.1 Verified Java defects

| # | Finding | Evidence | Resolution |
|---|---|---|---|
| J-1 | The `CaptureRecord` envelope's own bytes are never budgeted. `bufferSize = messageSize - 500` (`KafkaCaptureFactory.java:265` -> `:981`) is the per-record protobuf limit, and `payloadSizeLimit = maximumKafkaMessageSize - 500` (`CaptureKafkaPublisher.java:329`) is the publisher ceiling. `KafkaCaptureFactory.java:718` passes `bufferSize + 500` as `maximumKafkaMessageSize`, so the two limits are **the same number** — yet `CaptureKafkaPublisher.java:495` compares the *enveloped* `CaptureRecord` length (`TrafficStream` + 1 tag byte + a varint length) against it. One byte over is a terminal `PAYLOAD_LIMIT` capture failure. Java survives only because the closing `index` field is accidentally reserved twice, leaving ~6-7 bytes of slack against the 4-5 bytes needed; at an 8 MiB configuration the margin is ~1-2 bytes. | Cited lines verified directly by the integrator. | **FIXED in Rust.** The encoder budgets `payload_limit - (1 + varint_len(payload_limit))` for the `TrafficStream`. This shifts record-packing boundaries by a few bytes. Sanctioned: the rewrite plan states exact Java record-packing boundaries are not required absent a consumer dependency, and the replayer does not read record indices. |
| J-2 | Terminal flush with no open record fabricates an empty final record, which then trips the terminal-rule check at `KafkaCaptureFactory.java:1274-1290` and declares the process unstable. Latent. | Reported with citations in the wire spec. | Rust never emits an empty record; terminal publication detaches only a nonempty record. |
| J-3 | The pass-through teardown path (`LoggingHttpHandler.java:352-354`) neither publishes a terminal record nor releases the open record, leaking a pooled `ByteBuf` and leaving the `ConnectionRoute` registered forever, which blocks writer-partition retirement. Reachable. | Reported with citations in the wire spec. | Rust uses RAII-owned record buffers released exactly once on success, rejection, and failure, and deregisters the route on every teardown path. |
| J-5 | `connectionException` is unsegmentable, so a long `Throwable.getMessage()` is a hard capture failure. | Reported with citations in the wire spec. | Rust bounds the exception message before encoding. Recorded; no wire change. |

### 3.2 Document-versus-code disagreements

| # | Doc says | Code does | Resolution |
|---|---|---|---|
| D-1 | `proxyCaptureProtocol.md` §10.1 requires a **positive** configurable `F`. | `StreamChannelConnectionCaptureSerializer.java:152-154` accepts `F = 0` and silently disables record deadlines. | Implement the **documented** behavior: reject non-positive `F` at startup. Silently disabling the record-boundary deadline would void the §4.2 content-boundary invariant. |
| D-2 | §4.1 calls `connectionObservationSequence` "monotonically increasing". | The replayer requires **exactly +1** and rejects an absent field (`SourceConnectionState.java:740-745`). | Implement the stricter real contract: contiguous +1, always present. The doc wording is looser than the consumer. |
| D-3 | §9 assigns record-index continuity validation to the replayer. | The replayer never reads the index; `TrafficStreamUtils.java:62-64` uses it only as a tracing label. | Rust still emits correct, contiguous indices and the `numberOfThisLastChunk` terminal marker (producer-side invariant, enforced as a biconditional exactly as `KafkaCaptureFactory.java:1274-1290` does). No consumer dependency exists, so this constrains only the proxy. |
| D-4 | §4.1/§5.1 treat `DisconnectObservation` as a live non-terminal observation. | It has no emitter in the proxy and no reader on the replay path. | Keep the field in the schema (frozen). Do not emit it. Recorded so a future reader is not surprised by its absence. |
| D-5 | The protocol document is **completely silent** on segmentation and on interim (1xx) responses — zero mentions — although both are mandatory, replayer-validated wire behavior. | Both are implemented and tested in Java. | Implement from the Java behavior and the test suite, which are the real contract here. Flagged as a documentation gap, not an implementation choice. |
